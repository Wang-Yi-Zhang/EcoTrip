# SDD-002：代墊與付款管理

- 日期：2026-11-16
- 狀態：設計定案（2026-11-16 三輪問答，18 項決定由使用者確認；同日依使用者要求改為每筆可寫房間分法）。第 2 到 4 步都已完成：計算核心（`EcoCore.computeLedger`，`docs/tests/ledger.test.mjs` 44 項）、`gas/Code.gs`（`gas.test.mjs` 19 項）、「分帳」分頁。尚未重新部署到使用者的試算表，也還沒用真實帳本與 Splitwise 交叉比對。
- 範圍：記錄旅伴之間誰替誰付了多少、每筆的付業者期限與還款期限，算出每人淨額與結清方式。不處理實際轉帳，也不連銀行。

## 問題與現況證據

- 已經發生代墊：AirAsia 國際線 4 人合計 TWD 68,357.60，其中使用者本人 17,570.62、另外三人 50,786.98（`docs/PROGRESS.md`）。三人各自的金額不同（加購不同），要看訂位確認信才知道。AirBorneo 國內線 4 人 TWD 14,135、Lahad Datu 1/31 住宿 4 人 TWD 1,800 也是一人先付。
- 接下來的大額付款：DVFC 付清期限 2026-11-30（不可退訂金 60%，`docs/05`）、Tabin 報價 RM 26,320（付款條款未知）。代墊人的資金壓力就在付業者期限和旅伴還款之間。
- 網站是公開的 GitHub Pages；`gas/Code.gs` 的 `doGet` 是公開唯讀端點，檔頭規定不放個資。費用試算 `EcoCore.computeBudget` 只算「整團要花多少」，沒有「誰付了、誰該負擔」的概念。

## 決策

### D1 資料放哪裡、誰能寫

1. 帳本放在現有 Google 試算表新增的兩個工作表：`members`、`ledger`。人員一律用暱稱。
2. 只有使用者能在試算表裡編輯。網站只讀，**不加 `doPost`**，`doGet` 維持唯讀。之後要讓旅伴自己回報，再加 Google 表單（寫進另一個回應工作表，由使用者確認後轉進 `ledger`）。
3. `doGet` 會把兩個工作表一起回傳，所以拿到網址的人都讀得到。可接受的前提：只放暱稱、金額、日期、用途與憑證位置；**不放姓名、帳號、訂位代號、護照、卡號**；`note` 欄不回傳。端點網址只私下給旅伴（網址目前只存在各自瀏覽器的設定裡，不在 repo）。
4. 網站**沒有內建帳本**（不加 `data-ledger` 區塊），repo 裡只有測試用的虛構資料（暱稱 A、B、C、D）。沒有設定端點時，「分帳」分頁顯示設定說明。

### D2 工作表欄位

`members`：一列一位旅伴。

| 欄位 | 內容 |
|---|---|
| `nick` | 暱稱，唯一 |
| `room` | 預設房間代號（同房的人填同一個代號）。只有房間類費用、而且該筆沒寫 `rooms` 時才用到 |
| `status` | `active`／`withdrawn` |
| `withdrawn_on` | 退出日期 |
| `confirmed_through` | 這位旅伴已核對到的最後一筆 `ledger.id`，由使用者在旅伴回覆後代填 |

`ledger`：一列一筆事件，只新增、不修改。

| 欄位 | 內容 |
|---|---|
| `id` | 唯一編號，建議 `L001` 起依序 |
| `date` | 事件日期（付款、還款、退款的實際日期；`plan` 填建立日） |
| `type` | `plan` 預計付款／`payment` 付款／`share` 指定分攤／`repayment` 旅伴還款／`refund` 業者退款／`reversal` 沖銷 |
| `payer` | 付錢的人（`repayment` 是還錢的人） |
| `to` | `all`、或以分號分隔的暱稱；`repayment` 是收錢的人；`share` 是負擔的那一位 |
| `rooms` | 這一筆的房間分法（住宿用，選填）：`\|` 分隔房間、`;` 分隔同房的人。例如兩兩一間 `A;B\|C;D`、四人一間 `A;B;C;D`。適用 `payment`、`refund`、`plan` |
| `amount`、`currency` | 原幣金額與幣別（TWD、MYR、USD） |
| `home_actual` | 卡片或銀行實際入帳的結算幣別金額（沙巴是台幣）；還沒入帳就留空。欄名不寫幣別，因為核心是通用的 |
| `cost_id` | 對應 `costs` 的費用項目 id（可空，例如現場小額） |
| `vendor_due` | 付業者期限（`plan` 必填） |
| `repay_due` | 旅伴還款期限；留空時 = `date` + 7 天 |
| `evidence` | 憑證位置，例如「Gmail 2026-11-15 AirAsia 確認信」，不放內容 |
| `ref_id` | 關聯的另一筆：`reversal` 指被沖銷的那筆；`share` 指它分攤的 `payment`；`payment` 指它結掉的 `plan`；`refund` 指原本的 `payment` |
| `note` | 私人備註，`doGet` 不回傳 |

> 與問答時的差異：Q11 的「沖銷對象 id」改名為 `ref_id` 並擴大用途，讓 `share`、`payment`、`refund` 都能指回相關的那筆。少一欄，規則一樣。「實際台幣」欄名改為 `home_actual`。

`setupSheets()` 補上兩個工作表、表頭與下拉選單（`type`、`currency`、`status`；`payer` 從 `members.nick` 取值；`to` 可以填多人，所以是文字欄，由網站檢查暱稱），三個日期欄只接受日期。`type`、`status` 的允許值也由網站的 `EcoCore.allowedValues` 產生（`ledger_type`、`member_status`）。

### D3 計算規則（純函式，放在 EcoCore）

新增 `EcoCore.computeLedger(members, ledger, opts)`，和畫面分開；`opts` 帶入目前匯率與 `costs`。回傳每人分攤、已付、淨額、到期清單、結清建議與警告。核心不含沙巴專有內容，每趟旅行用自己的帳本。

1. **金額單位**：一律換成結算幣別（沙巴是台幣）的「分」（整數）再計算。以 `home_actual` 為準；空白時用臺銀現金賣出匯率暫估（同 `trip.currency` 的匯率設定），該筆標成「暫估」。
2. **淨額**：淨額 = 已付 − 應分攤 + 已還出 − 已收回。正數代表別人欠他。所有人淨額加總必須為 0。
3. **分攤**：
   - 一筆 `payment` 有 `ref_id` 指到它的 `share` 列時，照 `share` 的金額比例分配實際入帳金額，`share` 加總必須等於該筆付款的原幣金額（不相等就警告並改用 `to` 平分）。一列 `share` 的 `to` 可以寫多人，表示這筆金額由他們平分（例如只知道「另外三人合計」時）。
   - 沒有 `share` 列時，由 `to` 的成員平分。要按房間分時，先按房間平分，再由同房的人平分；房間分法依序取：該筆的 `rooms` 欄（有填就一定按房間分，不管費用項目）→ `cost_id` 是房間類（`per_room`、`per_room_per_night`）時用 `members.room`。
   - **各晚的房間分法不同**（例如某晚四人一間、其他晚兩兩一間）：每種分法各記一筆付款；一張帳單涵蓋好幾晚時，拆成幾筆，或用 `share` 列寫明各人金額。對象沒有列進任何房間時當作自己一間；房間裡的人不在對象中就不分攤；這兩種情況和同一人列兩次都會警告。
   - 補充：每間房人數相同時（四人一間、兩兩一間），按房間分和按人平分的結果一樣；只有人數不同（例如 2 + 1）時才有差別。
   - 單人房差價、個人加購、沒參加的活動，都用 `to` 或 `share` 指定給當事人。
4. **尾數**：除不盡的幾分錢由付款人吸收；付款人不在 `to` 裡時，由 `to` 中依 `members` 順序排第一位的人吸收。
5. **手續費**：海外刷卡手續費另記一筆 `payment`（`to = all`）。
6. **退款**：`refund` 列降低付款人的已付，並降低 `to` 指定者的分攤。
7. **退出**：`withdrawn` 的成員不再出現在之後 `to = all` 的分攤中；已付給業者、不可退的部分照原本分攤由他負擔，可退部分扣掉手續費後用 `refund` 列退給他。
8. **預計付款**：`plan` 列和還沒付款的 `costs` 項目只顯示為「預計」，**不算進淨額與結清**。同一個 `plan` 可以有多筆 `payment` 用 `ref_id` 指到它（例如先付訂金再付尾款）；付款的原幣合計達到 `plan` 金額才算結掉（幣別不同時改用結算幣別比較）。
9. **沖銷**：`reversal` 讓被指到的那筆完全失效；更正 = 沖銷舊的 + 新增正確的。

### D4 時間與結清

- 每筆款項追蹤三個時間：`vendor_due`（付業者期限）、`repay_due`（旅伴還款期限）、`date`（實際日期）。
- **滾動結清**：每筆 `payment` 之後，列出「誰在什麼期限前還給付款人多少」。這是兩人之間直接對應，每筆都能追溯到是哪一次付款。
- **最終結清**：回國、卡片帳單全部入帳、暫估都換成實際台幣後，用淨額算最少轉帳（貪婪法：最大債權人與最大債務人互相抵銷，4 人最多 3 筆）。最少轉帳會跨人抵銷，所以單筆轉帳不一定對應單筆費用；畫面改用每人淨額的組成明細說明它從哪裡來。

### D5 畫面

新增「分帳」分頁：

- 每人一列：應分攤、已付、已還、淨額；有暫估金額時標示。
- 到期提醒：快到的 `vendor_due` 與 `repay_due`，逾期的標紅。
- 結清：滾動結清清單；全部入帳後顯示最少轉帳建議。
- 預計：還沒付的金額與期限，讓代墊人知道要準備多少錢。
- 個人明細：選一位暱稱，列出他相關的每一筆，方便截圖給本人核對；有超過 `confirmed_through` 的新款項時標示「待確認」。
- 警告：見下方「檢查」。

## 檢查（網站讀到帳本時執行，不通過就顯示警告）

1. 所有人淨額加總 = 0。
2. 每筆有 `share` 的付款：`share` 加總 = 付款金額。
3. `id` 唯一；`ref_id` 指到存在的列；被沖銷的列沒有被沖銷第二次。
4. `payer`、`to` 的暱稱都在 `members` 裡；`withdrawn` 成員在退出日之後沒有出現在 `to = all` 的分攤中。
5. 幣別是 `trip.currency` 允許的值；`twd_actual` 與「原幣 × 匯率」相差超過 5% 時提醒（可能抄錯）。
6. 有 `cost_id` 時，它存在於 `costs`。

## 第 4 步實作紀錄（2026-11-16）

- `validateEnvelope` 把 `members`、`ledger` 放在回傳的 `ledger`，不放進 `accepted`：帳本沒有內建版本，不參與行程資料的覆蓋、參照檢查與回退。只有帳本、沒有其他資料集的回應也算成功。`validateLedgerDataset` 只檢查形狀（`items` 陣列、每列是物件、值只能是文字／數字／布林／null），內容規則交給 `computeLedger` 以警告顯示。
- 網站把帳本放在 `App.ledger`；改回本機資料或讀取失敗、沒有快取時清空。快取與其他遠端資料相同，存在這台瀏覽器的 localStorage。
- 分頁內容：已付總額與暫估筆數、結清狀態、帳本檢查、每人淨額（含「待確認」筆數）、到期的還款（逾期標示）、預計要付的錢（`plan` 列與費用試算中還沒有付款紀錄的項目）、最少轉帳（不是最終結清時標「參考」）、個人明細（可切換暱稱、被沖銷的列加刪除線）。
- 瀏覽器驗證（內建瀏覽器，`http://localhost:8765`）：用虛構暱稱 A–D 的 9 列測試帳本（放在遠端快取，網址是假的，所以走「離線，使用上次的資料」路徑），確認金額、暫估、逾期、預計付款、錯誤列警告、個人明細切換都正確；桌面與 375 px 手機寬度都沒有水平溢出，底部 7 個分頁各 52 px。主控台只有假網址造成的連線錯誤。測試資料驗證後已從瀏覽器清除。
- 已知取捨：「到期的還款」照每筆付款列出，兩人之間可能互相都有待還（例如 A 欠 B 一筆、B 欠 A 另一筆）。這是為了每筆都能追溯；要互相抵銷，看「最少轉帳」。
